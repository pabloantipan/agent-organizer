# CLAUDE.md — organizer

Wails v2 desktop app plus CLI, Go backend, React + TypeScript frontend. It scans
configured roots for `working-on/initiative.yaml`, reads the Kanban cards next to
it, and shows one merged board. It is read-only over the card files. With
`auth: firebase` it also pushes one snapshot per machine to Firestore under
the signed-in user and pulls every machine's.

## Initiative

This directory is an initiative root: it holds copies of the repos listed in
`working-on/initiative.yaml`. Work happens here and is ported back later.

- Current state lives in `working-on/*.md` (cards) and nowhere else. Read the
  open cards' frontmatter at session start. Update the card whose next action
  changed when you finish a piece of work. Follow the `working-on` skill.
- Repos inside this root are ported elsewhere. Never create `working-on/` or
  initiative files inside them.

## Layout

- `main.go` dispatches: a known subcommand runs `internal/cli`, anything else launches the app.
- `app.go` is the Wails-bound surface; it only calls `internal/service`.
- `internal/service` sequences scan, cache, sync, merge. CLI and app both use it.
- `internal/scan` finds initiatives and parses cards. The reference behaviour is
  `~/.claude/skills/working-on/hooks/working-on-session`.
- Manual priority is `model.Order` (initiative ids, card slugs per initiative, rail groups, the human's card notes, and the resolved marks of the human's queue). It is app state in the cache and one Firestore document `users/{uid}/meta/order` (last writer wins), never a card field. `merge` applies it to the board and to `organizer status`.
- Identity is a mode: `auth` in config, `off` (the default) or `firebase`, resolved by `config.AuthMode` — anything but an explicit firebase is off, so a typo cannot put a sign-in screen in front of the board. Off means the organizer has no identity: `Service.Account` is the empty account whatever the keychain holds, `SignIn`/`SignUp` refuse with `service.ErrAuthOff`, comments are signed by the machine, `Sync` returns `Skipped: "auth off"` with no error, the CLI's login, logout and whoami print one line and exit 0, `doctor` prints `auth: off`, the gate skips the sign-in screen and never reads `offlineChoice` (`gateStep` in `Gate.tsx`, the whole decision in one function), and the top bar drops the account menu and the Sync button. Firebase is exactly the behaviour below. The lock is independent of the mode: with auth off a forgotten passcode is recovered by deleting the keychain item (`security delete-generic-password -s cl.antipan.organizer -a passcode`), not by signing in. When identity comes it is Azure Entra ID, not this email flow; the Firebase code stays behind the switch until then (`~/agent-slack/docs/decisions.md`, 2026-09-16).
- Identity, `auth: firebase`: `internal/auth` is Firebase Authentication over REST (sign in, sign up, refresh, reset); `auth.Manager` keeps the ID token in memory and the refresh token in the Keychain (`internal/keychain`, service `cl.antipan.organizer`, items `refresh_token`, `account_email`, `passcode`). The refresh token is never written anywhere else. `internal/lock` is the local passcode (argon2id, 5 failures then 30 s cooldown); a cloud sign-in also unlocks and may reset it.
- `internal/sync` is Firestore native over REST (`BaseURL` swappable for tests): `users/{uid}/machines/{machine}/initiatives/{id}` with a JSON `payload` field, `users/{uid}/meta/order`. Rules in `firestore.rules`, database `organizer` (a second named database; the project's default one is Datastore mode and stays untouched). Each machine writes only its own subtree. Signed out is a skip, not an error. `internal/merge` builds the board; local wins.
- Board interaction model is Trello's, not its code: a left rail of initiatives (boards) by priority with drag to reorder, optionally partitioned into named groups (`model.Order.Groups`, synced with the order; `Regroup` derives the flat priority from group order so rank numbers stay global, `Reprioritize` keeps groups sorted after a flat reorder; the rail seeds groups from client, renames on double-click, drags across groups and reorders group headers, and initiatives in no group trail the last one), three fixed columns, card drag within a column only when one initiative is selected, and a centered card back. Drag is `@hello-pangea/dnd`. Cross-column drag stays disabled because it would write a status. A fourth Done column appears only with one initiative selected, collapsed, newest first, capped at 10, read-only.
- Visual direction (Pablo's pick): dark only, warm near-black with a purple cast (#1a1523), one solid electric purple accent (#8a3ffc), magenta as a tone, red for blocked. No gradients, no two-tone buttons, no white cards, no light theme. Statuses: now light purple, blocked rose, next periwinkle, done dim. Manrope Variable bundled via fontsource. Tokens in `frontend/src/styles/tokens.css`; the rules, contrast numbers and component anatomy in `docs/design-system.md` (Radix-style 12-step plum and violet scales as hex, since the WKWebView floor is Safari 15.0: no oklch, color-mix, nesting or @layer; seven type sizes; radii 4/6/8/12; the accent is a fill, accent text is `--accent-fg`). Legacy token names are aliases being migrated away.
- `frontend/src`: zustand store, plain CSS tokens, `hooks/useWails.ts` wraps the
  generated bindings in `frontend/wailsjs`.
- Navigation (`docs/specs/redesign.md` FR-14): Home, one initiative, or Settings (`screen` in `board.store.ts`). The app opens on Home (`Home.tsx`): Needs me, then the initiatives in the rail's order, each with its goal or "no goal yet", a stage stepper, its signals, and its next real date (card `due`, milestone or `target`, never computed); a row's chevron shows what the Initiatives tab used to (repos, problems, editor, terminal, review prompt; `InitiativeDetail` in `Initiatives.tsx`). Selecting an initiative in the rail or on Home shows `InitiativeHeader.tsx` (goal, measure, target, the decisions waiting, the stages with the current one marked) over six sub-views (`sub`): Overview (`Overview.tsx`), Work (`Board`), Roadmap (`RoadmapView`, with a Cards | Calendar switch), Decisions (`DecisionsView`), Conversations (`SlackView`, the Slack tab renamed) and Agents (`AgentsView`). Settings sits behind the ⚙ in the top bar; the crumbs say where you are. The store's `goHome()`, `openInitiative(id, sub)` and `openNeedsMe(key)` (key `decision:<initiative>/<NNNN>`, `thread:<id>` or `card:<initiative>/<slug>`; Home scrolls to that row and highlights it) are how any view navigates; picking another initiative keeps the sub-view. There is one badge, Needs me in the top bar, and it is the number of Needs me rows (`needsMeRows` in `lib/queue.ts`: the decision records waiting on a ruling plus `queueOf` over every cell plus deaf and capped seats, oldest first, then one undated row per local cell in definition that is not a draft, gone once a seat has run; one verb per row: Rule, Answer, Open, Agents, Launch, which opens the initiative's Agents). No sub-view carries a badge. Rule opens the record in the initiative's Decisions for now; the row's action is its own component (`DecisionRow`, `RuleAction` in `Home.tsx`) so the rule box replaces it alone. The shell's styles are `styles/shell.css`, tier-2 tokens only.

- Planning dates: card `due`, initiative `target` and `milestones` (all optional, all must be real; the skill forbids invented dates). Calendar, inside Roadmap, is a month grid of dues, milestones, and targets with an overdue and next-30-days agenda. `frontend/src/components/Roadmap.tsx` is a Gantt: one row per open card over a shared axis, milestones and target on the axis, today as a line. Bar start = card `start`, else the branch's first commit from git (`scan.branchSpans`, main/master excluded), else `updated`; bar end = `due`, else today for `now`, else the branch's last commit. No span means a dot. It lives only in the Roadmap sub-view (`RoadmapView.tsx`), under the initiative's header, with Calendar a switch away; `Portfolio.tsx` (one Gantt row per initiative) is no longer mounted, since Home's initiative rows replace it. Work, Calendar and Home do not embed it. Never use chips for initiative selection; the rail scales, chips do not. The rail collapses laterally to a 46 px strip of rank numbers (`railCollapsed` in the store, remembered per machine; hover the rail for the toggle) with the initiative id and counts on hover. `App.MilestoneType` and `App.StageType` exist only so Wails emits the nested types.
- Goal and stages: `initiative.yaml` carries an optional `goal` (the outcome in one line), `measure` (how the owner knows it worked), `specs` (the paths the specification lives in, read verbatim) and `scope` (`{in, out}`, two lists in the owner's words, `model.Scope`; none is two empty lists on the board, never null, and no problem), all on `model.Initiative` and so on every `BoardInitiative`. `working-on/roadmap.yaml` is the stages in order (`scan.readRoadmap` into `model.Stage`: `id`, `title`, `outcome`, `phase` (`discovery` or `building`), `exit` as a string or `{text, met}`, `gates`, `appetite`, `target`, `done`); the current stage is the first without `done`, stamped `current` by the scan, and `model.CurrentStage` reads the same rule. No roadmap means no stages and no problem. A card or a decision record joins a stage with `stage:`. A malformed roadmap is kept and reported, never a failed scan: a stage with no id, a duplicate stage id, a gate naming no decision record, a `stage:` naming no stage, a `target`, `met` or `done` that is not a real date, a `phase` that is neither `discovery` nor `building` (the stage is kept with no phase), and a `building` stage whose nearest phased predecessor is `discovery` and none of whose gates names an existing record (gates match with zero-padding, `4` is 0004; a roadmap that starts in building needs no gate) are one problem each (`checkStages`, `checkStageLinks`). The format is the working-on skill (Roadmap), the method the `roadmapping` skill; the fixture roadmap under `testdata/home/init-a/` is deliberately broken in four ways, one per case; the overlay under `testdata/fixture-overlay/` gives its stages phases and a gate written `4` for record 0004.
- Decisions: `working-on/decisions/<NNNN>-<slug>.md` records (the working-on skill, Decisions): ADR-shaped, `proposed | ruled | superseded | withdrawn`, with `raised`, `owner`, `ruled`, `ruled_by`, `options`, `chosen`, `cards`, `supersedes`. `scan.readDecisions` reads them into `ScannedInitiative.Decisions` and reports broken ones as problems (a ruling on a proposed record, a ruled one without `ruled_by`, a dangling supersede); `merge` carries them on `BoardInitiative`. The Decisions sub-view (`DecisionsView.tsx`) shows the queue waiting on a ruling oldest first, a raised → ruled timeline, and the median turnaround; it has no badge, the waiting records are rows of Needs me and a count in the initiative header. `organizer decisions [initiative] [--json]` prints the same. The one thing the app writes into a record is a ruling of a `proposed` one, whoever owns it, from the Decisions tab or Needs me (`internal/service/rule.go`, `Service.RuleDecision`, bound as `App.RuleDecision`, `organizer rule <initiative> <NNNN> --chosen <option> --words <text>`, 0019, 0045): `status: ruled`, `ruled` (today), `ruled_by` (the ruler, not the owner: the cell's `human`, else pablo, since with auth off the organizer has no identity; `ruler` in `rule.go`, `leadOf` for the box's label) and `chosen`, plus the words under `## Ruling` signed "<ruler>, <date>, owner <owner>, in the organizer on <machine>", the owner named only when someone else ruled. A record with no owner is ruled. The record is edited as text so every other byte survives, and that one file is committed by shelling out to git. It refuses a record that is not proposed, a `chosen` outside `options`, and empty words, and writes nothing when it does; it writes no recommendation, no proposal and no other field. Waiting is fuchsia and dashed, ruled the accent family, a pair validated for colour vision.
- Agents: `scan.Agents` joins three sources: the process table (`ps`, processes whose binary is `agent_binary`, default claude; `-n`/`--resume` args give the session name; `lsof -d cwd` gives the directory), `zellij list-sessions -n`, and the probe layouts in `probe_state_dir`. States: working (CPU time grew since the previous sample, tracked in `Service.prevCPU`), running, shell (session without an agent process), exited (layout only). `AssignAgents` groups by longest initiative root prefix of the cwd, then probe family — the initiative's id or, for a crew seat, the cell's project, since `camp-probe-andrea` belongs to `ccint-camp-monorepo`; the rest are `unassigned_agents`. `App.agentTicker` samples every 10s while the window is open (`RefreshAgents`: processes and sessions only, no git) and emits the Wails event `agents`; the store's `applyAgents` patches live/working counts into the board so rail, Home, the header and Agents all move without a rescan. No daemon: nothing runs when the app is closed. Lifecycle goes through `~/bin/probe` so layouts, markers and iTerm profiles stay consistent: New agent = `probe --wrap <initiative>` then `<initiative>-probe <name> <dir>` (or `-t` for an animal name) in a new iTerm window; Kill = `probe -k <session>` (conversation stays resumable); Stop = SIGTERM to a plain-terminal pid after re-checking its binary. Working = CPU rate over the sample interval >= 1% of a core. Attach = iTerm2 profile named after the session, Terminal `probe <name>` fallback. `organizer agents` prints the grouping.
- Crew: an initiative root with `agents/cell.json` (persona-agents skill) has a cell. `scan` reads it into `ScannedInitiative.Cell`; the process scan uses `ps -E` and reads only `AGENT_NAME`, `PROJECT_ID`, `AGENT_SESSION` from each agent's environment (never the token) into `Agent.Persona`, `Cell`, `Session`. `service.buildCrew` joins the roster to the agents by persona, else by the crew session name (`service.crewSession`), and stamps discuss health (`internal/discuss`, read-only client over the unix socket, GET `/projects/{project}/health` as the cell's human, token from `tokens.json` in `discuss_state_dir`). `CreateCrew` (`organizer crew <id> [--print]`, the Bring crew up button) preflights `discuss-api token env` per seat, writes `~/.local/share/organizer/crew/<id>/<seat>.sh` (a prelude that exports the identity by running `token env` at launch, so no token is stored, `AGENT_SESSION` with the name the pane is launched under, and `ANTHROPIC_MODEL` from `crew_model` in config, default opus, overridable per cell with a `model` field in `cell.json`; the env var outranks the settings file's model) and `<seat>.md` (`prompt.Persona`), then runs `PROBE_PRELUDE_FILE=… PROBE_PROMPT_FILE=… <project>-probe <short seat> <root>` in one iTerm2 window, one tab per seat. Probe sources the prelude on every start and sends the prompt on the first run only. An initiative without a cell offers Draft the cell on its Agents sub-view and `organizer draft-cell <id> [--print]` (`internal/service/draft.go`, `prompt.DraftCell`, discovery-in-a-cell FR-3): with a `goal`, `agents/people.md` and no `cell.json` it writes `~/.local/share/organizer/prompts/<id>-draft-cell.md` and opens a Terminal at the root running `<agent> "$(cat file)"` told to follow the persona-agents skill's `references/drafting.md` and write only under `agents/` and `working-on/decisions/`; the session's `cell.json` carries `draft: true` and `drafted`, a draft is in definition waiting on its proposed `NNNN-the-cell-roster` record, `CreateCrew` refuses it naming that record, and accepting is that record's ruling; there is no accept button.

- Crew session names: `crewSession` in `internal/service/crew.go` is the one place a seat's session is named, and it is `<cell project>-probe-<seat short name>` — `camp-probe-andrea`, not `ccint-camp-monorepo-probe-po_andrea`. The short name is the seat after its role prefix (`<role>_<name>`, the role may hold underscores: `tech_lead_nicolas` → `nicolas`). The ceiling is `maxSessionName`, 68: zellij puts the socket at `$TMPDIR/zellij-<uid>/contract_version_1/<name>`, macOS caps a socket path at 103 characters, and probe (with `gen-probe-profiles` and `files`) runs zellij with `TMPDIR=/tmp`, a 35-character prefix for uid 501 (measured on zellij 0.44.3: 68 starts, 69 is refused; under the per-user default TMPDIR it was 22). Over it `crewSession` returns an error naming the length, never a truncation, `CreateCrew` refuses before it creates anything, a retire plan reports the seat it cannot name, and probe itself refuses. Launch, the join and the retire all read this one function and `sessionNameTooLong`; the constant moves only if probe's socket dir does. Sessions started before the TMPDIR pin reached a machine keep their sockets under the default TMPDIR; probe lists, attaches and kills them there until they end.
- Two sub-views for agents, one question each. Agents is lifecycle: what runs, bring crew up, attach, kill, state, context, watcher, what a seat owes; Message on a row with a seat jumps to Conversations focused on that agent (`openSlack` in the store). Conversations (`SlackView.tsx`, `Conversation.tsx`; named Slack before the redesign, and the code keeps that name) is the agent-slack view remade the way Teams draws Chat. One definition of the queue lives in `frontend/src/lib/queue.ts` (`queueOf`: threads escalated or asking the human, plus cards whose next action matches `^(pablo|decide)\b` on this machine, minus `Order.Resolved`; deaf counted apart and capped never deaf) and every count uses it: Needs me on Home and its badge (`needsMeRows`), the Agents pill, the Conversations chat list. The server's `AgentGroup.NeedsMe` is threads only and ignores Solved marks; do not show it as the queue. "Needs me" means the human's queue and nothing else: threads escalated to the human, or with a message addressed to the human and no reply from the human after it (`CellThread.AskedOfMe`, `AskedBy`, computed in `factsOf` from each thread's messages, cached per thread in `Service.openers` and refetched when the message count moves). Stalled or undecided threads are the reconciler's backlog (`AgentGroup.NeedsReconciler`, the "needs <reconciler>" entry), shown so the human can see it without owning it. Messages addressed to the human are outlined in red with "→ you" and the thread divider says "asks you · <seat>"; the docked box defaults to the last asker. The needs-me entry is a worklist, not a filter (`NeedsMe` in `Conversation.tsx`): one row per thing asked of the human, from a thread (escalated or asks you) or from a card whose next action is addressed to the human (`^(pablo|decide)\b`, local cards only). Each row is solved on its own: Discuss opens the thread, or a new conversation about the card addressed to the seat the next action names with the human's notes as context; Rule settles it in place (`RuleBox` in `Conversation.tsx`): one `decision` into the thread (an escalated thread is reopened first) or a new thread `<slug>: <first line>` for a card, with the next action as the body's last line `Next action: …` addressed to the seat that acts, then the row is marked solved; the Solved list reads the ruling back from the thread (`Ruling`, latest decision, split on that line) so the queue never keeps a copy. The card's `next` stays the agents' to write; the decision is how it reaches them; Solved marks it in `Order.Resolved` (`thread:<id>` or `card:<initiative>/<slug>`, with the date; a thread the human answered leaves by itself). Solved rows sit collapsed at the bottom with reopen. `Order.Notes` (`<initiative>/<slug>` to a list of `model.Note`: id, by, at, text) are the human's comments on a card, Trello-style: a feed on the card back under "Comments", newest first, signed with the account email (else the machine), added with Enter, edited and deleted in place (`AddNote`, `EditNote` with empty text deleting). Never written to the card file; they ride the order document so they sync, and "Write about this card" and the queue's Discuss put them in the opening message as "Context from <human>:" (`notesAsContext` in `lib`). one initiative selected shows a chats list on the left (needs me, needs <reconciler>, channel, one direct chat per seat under People, then journal and archive; a thread is direct with a seat when the posters are only the human and that seat, or the human opened it to that seat and it has not answered, which is why `CellThread` carries `Opener` and `To`, resolved once per thread and cached in `Service.openers` under its own lock because the feed builds under the service lock; activity since a chat was last shown here is a count, seen times in browser storage), one chat's timeline in the middle (its threads oldest first, each under a sticky subject divider with status, the n/12 counter, cards, branch links and reopen/escalate/close; messages in time order with timestamps; the latest decision pinned; the view stays pinned to the bottom unless the reader scrolled up), and one message box docked at the bottom that posts into the thread last touched (click a divider or reply on a message; "new thread instead" and the + in the list switch it to a new-thread form with a subject). The People panel on the right toggles from the header (members button with live and deaf counts). Messages render by kind (question and answer bubbles with the sender band as header; claim, yield, status, done as one-line events; `parent_id` indented; long bodies clamp with show all). Any message can be branched: a new direct thread to its author with subject `re: <parent subject>` and the quote as the first lines; the view links parent and branches by that subject convention (`branchParent`), since the API has no parent-thread field. A subgroup chat (the human and several seats where all see everything) is not expressible: delivery is per addressee or whole-cell broadcast, so it needs thread members in the discuss API first. The composer keeps kind, recipient (direct by default) and the wake count visible on purpose: chat invites small messages and every wake is a turn. Everything but the shown chat's messages and the archive rides the 10 s agents feed (`AgentGroup.Threads`, `NeedsMe`, `Human`, `CanPost`); the shown chat polls every 5 s. Health words: the server's `deaf` means old undelivered mail whatever the cause; the organizer splits off `capped` (`discuss.AgentHealth.Capped`: a drain ran after the oldest undelivered message arrived and left it, so the session hit discuss's drain ceiling for this stop cycle; the seat is alive and posting, and the mail waits for its next prompt, the watcher's wake or anything typed into its pane, which delivers it: since agent-slack 8991640 the ceiling counts per stop cycle, so nothing is restarted for it). Capped is magenta, deaf is red; cards say "capped, mail waits for its next prompt" instead of "not picking up". Every health word, its why and what to do come from one table, `frontend/src/lib/health.ts`. Showing a chat of a cell picks up the human's mail (`Service.PickUp`, a drain with no session id so no ceiling applies): without it the human seat reads as deaf and cards say "pablo not picking up". The human's watcher still reads stale, since the app never long-polls. The app reads and posts as the cell's human seat (`internal/service/cell.go`, `internal/discuss/client.go`), never as a persona. Cards link to threads by `threads:` ids or a subject starting with the card slug (`discuss.SubjectSlug`); the app writes nothing to cards. The card back has a Discuss section: Slack per thread the card names (lands in the right chat with that thread targeted and scrolled to), and Write about this card (a seat picker, guessed from the next action's persona name, then Slack with the new-thread form prefilled `<slug>: `). Both go through `slackDraft` in the store, a one-shot instruction Conversations consumes and clears. An initiative without `agents/cell.json` has no mailbox and Slack says so.
- Retire and clean, the end of a wave (`internal/service/retire.go`, `organizer retire <id> [--seats a,b | --keep a,b] [--kill session] [--keep-threads] [--keep-tokens] [--no-commit] [--run]`, the Retire… button on a crew block, `organizer clean` and Clean exited on the Agents tab). `PlanRetire` resolves the options against the roster, the live zellij sessions, the token registry and the mailbox and changes nothing; the CLI is dry unless `--run`, the dialog shows the plan before Retire. `Retire` in order: kill the retired seats' crew sessions plus any named session (`probe -k`, conversations stay resumable); close every open thread of the project as the human and pick up the human's and the kept seats' mail (that is what clears "owes"); `discuss-api token rm` per retired seat then `launchctl kickstart -k` the discuss API, which loads tokens once at boot (other cells' watchers reconnect); delete the retired seats' crew prelude and prompt files; rewrite `agents/cell.json` keeping every other field and commit it when `agents/` is a git repo; prune statusline records of dead pids; rescan. Seats default to every one but the reconciler; `--retirable` (the "N retirable" state of the crew block, and the dialog's preselection) picks `service.Retirable`: seats that are not the human or the reconciler, named by no open card's `seat:` field, and not working, and then closes only the wave's own threads (every poster a retired seat or the human). A seat with an open card or a working session is kept and the plan says why; `--force` overrides. The supervise skill's step 8 runs this after the review; the card template carries `seat:` for it. `Clean` is `probe -c` plus the record prune, safe between waves. Without this each wave left its builders in the roster, off and owing mail, and the Agents view grew with every wave.
- Context fill: `organizer statusline` is the Claude Code `statusLine` command (`~/.claude/settings.json`). It parses the JSON on stdin (`session_id`, `transcript_path`, `context_window.used_percentage`, model, cost), resolves the agent pid by walking parents to the agent binary, writes `~/.local/share/organizer/sessions/<pid>.json` (`internal/session`), and prints the status text. The scan joins records by pid into `Agent.Context` and prunes records of dead pids after a two-minute grace. `organizer doctor` reports whether the statusLine is installed and whether discuss is running.
- Run gate: a card is launchable when it carries the working-on skill's build fields `spec`, `gate` and `boundary` (`model.Card`, yaml and json tags, filled by the scan; `depends_on` and `review` ride along). `organizer run <initiative> <card>` refuses with exit 2 naming the missing ones — a builder without a gate reports done by feel — and otherwise opens `service.launchLine` (PROBE_PRELUDE_FILE, PROBE_PROMPT_FILE, `<family>-probe <name> <dir>`, the supervise skill's step 4) in an iTerm tab, or prints it with `--print`. `CreateCrew` builds its seat commands with the same `launchLine`. The directory is the card's worktree under `.wt/` (`<branch>`, `<slug>`, then `<repo>-<slug>`) else the initiative root; the prelude is `prompts/opus.prelude.sh` and the task prompt `prompts/<initiative>-<slug>.md`, which the supervisor writes — a real launch refuses without it, `--print` only warns, as it does for a session name over `maxSessionName` (68, the Crew session names paragraph), which probe refuses.
- Runs baseline: a session record dies with its process, so `session.Retire` appends it to `~/.local/share/organizer/runs.jsonl` first — an open line the first time it is seen (the statusline writes no start time) and a final line when it is retired, folded by `pid:session_id`. Each line carries pid, session id, cwd, model, context, cost, first and last seen, and the card, matched by worktree path element first and the checkout's branch second (`session.MatchCard`; `Service.branchOf` reads the scan's repo states, then `.git/HEAD`, never git itself). Two cards answering to one directory leaves the run unattributed on purpose: a cost under the wrong card is worse than no cost. `organizer runs [initiative] [--json]` archives, then prints card, session, model, started, ended, wall, context at end and cost, newest first. This is the P0.6 baseline; no productivity claim without a number from it.
- Agent hand-off: `internal/prompt` renders a review prompt from the live scan (repos, open cards, next actions, staleness, scanner problems) plus the update rules of the working-on skill. `organizer prompt <id>` prints it; `--run` and the board button write it to `~/.local/share/organizer/prompts/<id>.md` and open a terminal at the initiative root running `<agent> "$(cat file)"`. The agent command is `agent` in config, default claude.
- Record: `internal/record` is the write-only client for discuss-record (spec authority: agent-slack `specs/factory-push-spec.md` §7–8, `specs/record-spec.md` §4). `organizer factory-key [--rotate]` signs the developer in, POSTs `/v1/factories/keys` with the ID token and writes `~/.local/state/discuss/push.key` 0600; `--rotate` issues, writes, then revokes the old key by sha256, in that order. The factory id is `<state>/factory`, written once from `machine`. `CreateCrew` writes the cell's `push` flag from `cell.json` into `<state>/projects.json` (merge, other cells kept) and, when `record_url` is set and a key exists, registers the cell (`POST /v1/factories/{f}/cells` with initiative id, title, client; 2xx or 409 both count as registered). The key is never logged and never stored anywhere else.

- Packaging: `make build|dmg|install|universal`, version from `git describe` into `main.version` via ldflags (`organizer version`, shown in the top bar). `scripts/make-dmg.sh` uses hdiutil only. `.github/workflows/release.yml` builds a universal app on tags `v*`, signs and notarizes only when the Developer ID secrets exist, and attaches the DMG to a GitHub Release. Bundle id `cl.antipan.organizer`, min macOS 12. Logs: `~/.local/share/organizer/organizer.log`.

## Commands

```bash
go test ./...                                  # unit tests, fixtures in testdata/home
UPDATE_GOLDEN=1 go test ./internal/cli/        # refresh the status golden file
cd frontend && npm test                        # vitest once over frontend/src/lib (make test runs it after go test)
go run . status | board | doctor | sync        # CLI against the real home
go run . prompt <initiative-id> [--run]        # agent review prompt, or open a terminal running it
wails dev                                      # app + http://localhost:34115 for browser dev
wails build                                    # build/bin/organizer.app
wails generate module                          # regenerate frontend/wailsjs after changing bound types
firebase deploy --only firestore:rules --project <p> # after editing firestore.rules
```

## Conventions

- Config: `~/.config/organizer/config.yaml`. Cache: `~/.local/share/organizer/state.json`.
- Bound Go types need json tags; the Wails generator turns a field-name collision into
  a duplicate TypeScript identifier (that is why the initiative's origin machine is `created_on`).
- `wails dev` builds into the same `build/bin/` as `wails build` and removes its binary on exit, leaving an empty `.app`. After any `wails dev` session, run `wails build` again before launching the app from Finder.
- Card statuses are a closed set: now, blocked, next, done. Do not add one here; change the skill.
