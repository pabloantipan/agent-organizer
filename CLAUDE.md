# CLAUDE.md — organizer

Wails v2 desktop app plus CLI, Go backend, React + TypeScript frontend. It scans
configured roots for `working-on/initiative.yaml`, reads the Kanban cards next to
it, pushes one snapshot per machine to Firestore under the signed-in user, pulls every machine's, and shows
one merged board. It is read-only over the card files.

## Initiative

This directory is an initiative root: it holds copies of the repos listed in
`working-on/initiative.yaml`. Work happens here and is ported back later.

- Current state lives in `working-on/*.md` (cards) and nowhere else. Read the
  open cards' frontmatter at session start. Update the card whose next action
  changed when you finish a piece of work. Follow the `working-on` skill.
- Repos inside this root are ported elsewhere. Never create `working-on/` or
  initiative files inside them.

## Layout

- `main.go` dispatches: a known subcommand runs `internal/cli`, anything else launches the app.
- `app.go` is the Wails-bound surface; it only calls `internal/service`.
- `internal/service` sequences scan, cache, sync, merge. CLI and app both use it.
- `internal/scan` finds initiatives and parses cards. The reference behaviour is
  `~/.claude/skills/working-on/hooks/working-on-session`.
- Manual priority is `model.Order` (initiative ids, card slugs per initiative, rail groups, the human's card notes, and the resolved marks of the human's queue). It is app state in the cache and one Firestore document `users/{uid}/meta/order` (last writer wins), never a card field. `merge` applies it to the board and to `organizer status`.
- Identity: `internal/auth` is Firebase Authentication over REST (sign in, sign up, refresh, reset); `auth.Manager` keeps the ID token in memory and the refresh token in the Keychain (`internal/keychain`, service `cl.antipan.organizer`, items `refresh_token`, `account_email`, `passcode`). The refresh token is never written anywhere else. `internal/lock` is the local passcode (argon2id, 5 failures then 30 s cooldown); a cloud sign-in also unlocks and may reset it.
- `internal/sync` is Firestore native over REST (`BaseURL` swappable for tests): `users/{uid}/machines/{machine}/initiatives/{id}` with a JSON `payload` field, `users/{uid}/meta/order`. Rules in `firestore.rules`, database `organizer` (a second named database; the project's default one is Datastore mode and stays untouched). Each machine writes only its own subtree. Signed out is a skip, not an error. `internal/merge` builds the board; local wins.
- Board interaction model is Trello's, not its code: a left rail of initiatives (boards) by priority with drag to reorder, optionally partitioned into named groups (`model.Order.Groups`, synced with the order; `Regroup` derives the flat priority from group order so rank numbers stay global, `Reprioritize` keeps groups sorted after a flat reorder; the rail seeds groups from client, renames on double-click, drags across groups and reorders group headers, and initiatives in no group trail the last one), three fixed columns, card drag within a column only when one initiative is selected, and a centered card back. Drag is `@hello-pangea/dnd`. Cross-column drag stays disabled because it would write a status. A fourth Done column appears only with one initiative selected, collapsed, newest first, capped at 10, read-only.
- Visual direction (Pablo's pick): dark only, warm near-black with a purple cast (#1a1523), one solid electric purple accent (#8a3ffc), magenta as a tone, red for blocked. No gradients, no two-tone buttons, no white cards, no light theme. Statuses: now light purple, blocked rose, next periwinkle, done dim. Manrope Variable bundled via fontsource. Tokens in `frontend/src/styles/tokens.css`.
- `frontend/src`: zustand store, plain CSS tokens, `hooks/useWails.ts` wraps the
  generated bindings in `frontend/wailsjs`.

- Planning dates: card `due`, initiative `target` and `milestones` (all optional, all must be real; the skill forbids invented dates). The Calendar tab is a month grid of dues, milestones, and targets with an overdue and next-30-days agenda. `frontend/src/components/Roadmap.tsx` is a Gantt: one row per open card over a shared axis, milestones and target on the axis, today as a line. Bar start = card `start`, else the branch's first commit from git (`scan.branchSpans`, main/master excluded), else `updated`; bar end = `due`, else today for `now`, else the branch's last commit. No span means a dot. It lives only in the Roadmap tab (`RoadmapView.tsx`), which shares the rail with Board and Calendar: nothing selected shows `Portfolio.tsx`, one Gantt row per initiative in priority order (earliest card or branch start to target, latest due, or today); an initiative selected shows its card-level Gantt. Board, Calendar, and Initiatives do not embed it. Never use chips for initiative selection; the rail scales, chips do not. The rail collapses laterally to a 46 px strip of rank numbers (`railCollapsed` in the store, remembered per machine; hover the rail for the toggle) with the initiative id and counts on hover. `App.MilestoneType` exists only so Wails emits the nested type.
- Agents: `scan.Agents` joins three sources: the process table (`ps`, processes whose binary is `agent_binary`, default claude; `-n`/`--resume` args give the session name; `lsof -d cwd` gives the directory), `zellij list-sessions -n`, and the probe layouts in `probe_state_dir`. States: working (CPU time grew since the previous sample, tracked in `Service.prevCPU`), running, shell (session without an agent process), exited (layout only). `AssignAgents` groups by longest initiative root prefix of the cwd, then probe family; the rest are `unassigned_agents`. `App.agentTicker` samples every 10s while the window is open (`RefreshAgents`: processes and sessions only, no git) and emits the Wails event `agents`; the store's `applyAgents` patches live/working counts into the board so rail, header, Initiatives, and the Agents tab all move without a rescan. No daemon: nothing runs when the app is closed. Lifecycle goes through `~/bin/probe` so layouts, markers and iTerm profiles stay consistent: New agent = `probe --wrap <initiative>` then `<initiative>-probe <name> <dir>` (or `-t` for an animal name) in a new iTerm window; Kill = `probe -k <session>` (conversation stays resumable); Stop = SIGTERM to a plain-terminal pid after re-checking its binary. Working = CPU rate over the sample interval >= 1% of a core. Attach = iTerm2 profile named after the session, Terminal `probe <name>` fallback. `organizer agents` prints the grouping.
- Crew: an initiative root with `agents/cell.json` (persona-agents skill) has a cell. `scan` reads it into `ScannedInitiative.Cell`; the process scan uses `ps -E` and reads only `AGENT_NAME`, `PROJECT_ID`, `AGENT_SESSION` from each agent's environment (never the token) into `Agent.Persona`, `Cell`, `Session`. `service.buildCrew` joins the roster to the agents by persona, else by the crew session name `<initiative>-probe-<seat>`, and stamps discuss health (`internal/discuss`, read-only client over the unix socket, GET `/projects/{project}/health` as the cell's human, token from `tokens.json` in `discuss_state_dir`). `CreateCrew` (`organizer crew <id> [--print]`, the Bring crew up button) preflights `discuss-api token env` per seat, writes `~/.local/share/organizer/crew/<id>/<seat>.sh` (a prelude that exports the identity by running `token env` at launch, so no token is stored, and `ANTHROPIC_MODEL` from `crew_model` in config, default opus, overridable per cell with a `model` field in `cell.json`; the env var outranks the settings file's model) and `<seat>.md` (`prompt.Persona`), then runs `PROBE_PRELUDE_FILE=… PROBE_PROMPT_FILE=… <family>-probe <seat> <root>` in one iTerm2 window, one tab per seat. Probe sources the prelude on every start and sends the prompt on the first run only.
- Two tabs for agents, one question each. Agents is lifecycle: what runs, bring crew up, attach, kill, state, context, watcher, what a seat owes; Message on a row with a seat jumps to Slack focused on that agent (`openSlack` in the store). Slack (`SlackView.tsx`, `Conversation.tsx`) is the agent-slack view remade the way Teams draws Chat: nothing selected lists every mailbox with what needs the human and what needs the reconciler; the tab badge is needs-me plus deaf seats. One definition of the queue lives in `frontend/src/lib/queue.ts` (`queueOf`: threads escalated or asking the human, plus cards whose next action matches `^(pablo|decide)\b` on this machine, minus `Order.Resolved`; deaf counted apart and capped never deaf) and every count uses it: the tab badge, the mailbox list, the Agents pill, the Slack chat list. The server's `AgentGroup.NeedsMe` is threads only and ignores Solved marks; do not show it as the queue. "Needs me" means the human's queue and nothing else: threads escalated to the human, or with a message addressed to the human and no reply from the human after it (`CellThread.AskedOfMe`, `AskedBy`, computed in `factsOf` from each thread's messages, cached per thread in `Service.openers` and refetched when the message count moves). Stalled or undecided threads are the reconciler's backlog (`AgentGroup.NeedsReconciler`, the "needs <reconciler>" entry), shown so the human can see it without owning it. Messages addressed to the human are outlined in red with "→ you" and the thread divider says "asks you · <seat>"; the docked box defaults to the last asker. The needs-me entry is a worklist, not a filter (`NeedsMe` in `Conversation.tsx`): one row per thing asked of the human, from a thread (escalated or asks you) or from a card whose next action is addressed to the human (`^(pablo|decide)\b`, local cards only). Each row is solved on its own: Discuss opens the thread, or a new conversation about the card addressed to the seat the next action names with the human's notes as context; Rule settles it in place (`RuleBox` in `Conversation.tsx`): one `decision` into the thread (an escalated thread is reopened first) or a new thread `<slug>: <first line>` for a card, with the next action as the body's last line `Next action: …` addressed to the seat that acts, then the row is marked solved; the Solved list reads the ruling back from the thread (`Ruling`, latest decision, split on that line) so the queue never keeps a copy. The card's `next` stays the agents' to write; the decision is how it reaches them; Solved marks it in `Order.Resolved` (`thread:<id>` or `card:<initiative>/<slug>`, with the date; a thread the human answered leaves by itself). Solved rows sit collapsed at the bottom with reopen. `Order.Notes` (`<initiative>/<slug>` to a list of `model.Note`: id, by, at, text) are the human's comments on a card, Trello-style: a feed on the card back under "Comments", newest first, signed with the account email (else the machine), added with Enter, edited and deleted in place (`AddNote`, `EditNote` with empty text deleting). Never written to the card file; they ride the order document so they sync, and "Write about this card" and the queue's Discuss put them in the opening message as "Context from <human>:" (`notesAsContext` in `lib`). one initiative selected shows a chats list on the left (needs me, needs <reconciler>, channel, one direct chat per seat under People, then journal and archive; a thread is direct with a seat when the posters are only the human and that seat, or the human opened it to that seat and it has not answered, which is why `CellThread` carries `Opener` and `To`, resolved once per thread and cached in `Service.openers` under its own lock because the feed builds under the service lock; activity since a chat was last shown here is a count, seen times in browser storage), one chat's timeline in the middle (its threads oldest first, each under a sticky subject divider with status, the n/12 counter, cards, branch links and reopen/escalate/close; messages in time order with timestamps; the latest decision pinned; the view stays pinned to the bottom unless the reader scrolled up), and one message box docked at the bottom that posts into the thread last touched (click a divider or reply on a message; "new thread instead" and the + in the list switch it to a new-thread form with a subject). The People panel on the right toggles from the header (members button with live and deaf counts). Messages render by kind (question and answer bubbles with the sender band as header; claim, yield, status, done as one-line events; `parent_id` indented; long bodies clamp with show all). Any message can be branched: a new direct thread to its author with subject `re: <parent subject>` and the quote as the first lines; the view links parent and branches by that subject convention (`branchParent`), since the API has no parent-thread field. A subgroup chat (the human and several seats where all see everything) is not expressible: delivery is per addressee or whole-cell broadcast, so it needs thread members in the discuss API first. The composer keeps kind, recipient (direct by default) and the wake count visible on purpose: chat invites small messages and every wake is a turn. Everything but the shown chat's messages and the archive rides the 10 s agents feed (`AgentGroup.Threads`, `NeedsMe`, `Human`, `CanPost`); the shown chat polls every 5 s. Health words: the server's `deaf` means old undelivered mail whatever the cause; the organizer splits off `capped` (`discuss.AgentHealth.Capped`: a drain ran after the oldest undelivered message arrived and left it, so the session hit discuss's drain ceiling of 8 per Claude session and mail waits for a new session; the seat is alive and posting but unreachable until restarted with `probe -r`). Capped is magenta, deaf is red; cards say "hit the drain ceiling, restart its session" instead of "not picking up". The ceiling itself is agent-slack's to fix (`DISCUSS_MAX_DRAINS`, or count block-drains per stop cycle instead of drains per session). Showing a chat of a cell picks up the human's mail (`Service.PickUp`, a drain with no session id so no ceiling applies): without it the human seat reads as deaf and cards say "pablo not picking up". The human's watcher still reads stale, since the app never long-polls. The app reads and posts as the cell's human seat (`internal/service/cell.go`, `internal/discuss/client.go`), never as a persona. Cards link to threads by `threads:` ids or a subject starting with the card slug (`discuss.SubjectSlug`); the app writes nothing to cards. The card back has a Discuss section: Slack per thread the card names (lands in the right chat with that thread targeted and scrolled to), and Write about this card (a seat picker, guessed from the next action's persona name, then Slack with the new-thread form prefilled `<slug>: `). Both go through `slackDraft` in the store, a one-shot instruction the Slack tab consumes and clears. An initiative without `agents/cell.json` has no mailbox and Slack says so.
- Retire and clean, the end of a wave (`internal/service/retire.go`, `organizer retire <id> [--seats a,b | --keep a,b] [--kill session] [--keep-threads] [--keep-tokens] [--no-commit] [--run]`, the Retire… button on a crew block, `organizer clean` and Clean exited on the Agents tab). `PlanRetire` resolves the options against the roster, the live zellij sessions, the token registry and the mailbox and changes nothing; the CLI is dry unless `--run`, the dialog shows the plan before Retire. `Retire` in order: kill the retired seats' crew sessions plus any named session (`probe -k`, conversations stay resumable); close every open thread of the project as the human and pick up the human's and the kept seats' mail (that is what clears "owes"); `discuss-api token rm` per retired seat then `launchctl kickstart -k` the discuss API, which loads tokens once at boot (other cells' watchers reconnect); delete the retired seats' crew prelude and prompt files; rewrite `agents/cell.json` keeping every other field and commit it when `agents/` is a git repo; prune statusline records of dead pids; rescan. Seats default to every one but the reconciler; `--retirable` (the "N retirable" state of the crew block, and the dialog's preselection) picks `service.Retirable`: seats that are not the human or the reconciler, named by no open card's `seat:` field, and not working, and then closes only the wave's own threads (every poster a retired seat or the human). A seat with an open card or a working session is kept and the plan says why; `--force` overrides. The supervise skill's step 8 runs this after the review; the card template carries `seat:` for it. `Clean` is `probe -c` plus the record prune, safe between waves. Without this each wave left its builders in the roster, off and owing mail, and the Agents view grew with every wave.
- Context fill: `organizer statusline` is the Claude Code `statusLine` command (`~/.claude/settings.json`). It parses the JSON on stdin (`session_id`, `transcript_path`, `context_window.used_percentage`, model, cost), resolves the agent pid by walking parents to the agent binary, writes `~/.local/share/organizer/sessions/<pid>.json` (`internal/session`), and prints the status text. The scan joins records by pid into `Agent.Context` and prunes records of dead pids after a two-minute grace. `organizer doctor` reports whether the statusLine is installed and whether discuss is running.
- Run gate: a card is launchable when it carries the working-on skill's build fields `spec`, `gate` and `boundary` (`model.Card`, yaml and json tags, filled by the scan; `depends_on` and `review` ride along). `organizer run <initiative> <card>` refuses with exit 2 naming the missing ones — a builder without a gate reports done by feel — and otherwise opens `service.launchLine` (PROBE_PRELUDE_FILE, PROBE_PROMPT_FILE, `<family>-probe <name> <dir>`, the supervise skill's step 4) in an iTerm tab, or prints it with `--print`. `CreateCrew` builds its seat commands with the same `launchLine`. The directory is the card's worktree under `.wt/` (`<branch>`, `<slug>`, then `<repo>-<slug>`) else the initiative root; the prelude is `prompts/opus.prelude.sh` and the task prompt `prompts/<initiative>-<slug>.md`, which the supervisor writes — a real launch refuses without it, `--print` only warns, as it does for a session name over probe's 22 characters.
- Runs baseline: a session record dies with its process, so `session.Retire` appends it to `~/.local/share/organizer/runs.jsonl` first — an open line the first time it is seen (the statusline writes no start time) and a final line when it is retired, folded by `pid:session_id`. Each line carries pid, session id, cwd, model, context, cost, first and last seen, and the card, matched by worktree path element first and the checkout's branch second (`session.MatchCard`; `Service.branchOf` reads the scan's repo states, then `.git/HEAD`, never git itself). Two cards answering to one directory leaves the run unattributed on purpose: a cost under the wrong card is worse than no cost. `organizer runs [initiative] [--json]` archives, then prints card, session, model, started, ended, wall, context at end and cost, newest first. This is the P0.6 baseline; no productivity claim without a number from it.
- Agent hand-off: `internal/prompt` renders a review prompt from the live scan (repos, open cards, next actions, staleness, scanner problems) plus the update rules of the working-on skill. `organizer prompt <id>` prints it; `--run` and the board button write it to `~/.local/share/organizer/prompts/<id>.md` and open a terminal at the initiative root running `<agent> "$(cat file)"`. The agent command is `agent` in config, default claude.
- Record: `internal/record` is the write-only client for discuss-record (spec authority: agent-slack `specs/factory-push-spec.md` §7–8, `specs/record-spec.md` §4). `organizer factory-key [--rotate]` signs the developer in, POSTs `/v1/factories/keys` with the ID token and writes `~/.local/state/discuss/push.key` 0600; `--rotate` issues, writes, then revokes the old key by sha256, in that order. The factory id is `<state>/factory`, written once from `machine`. `CreateCrew` writes the cell's `push` flag from `cell.json` into `<state>/projects.json` (merge, other cells kept) and, when `record_url` is set and a key exists, registers the cell (`POST /v1/factories/{f}/cells` with initiative id, title, client; 2xx or 409 both count as registered). The key is never logged and never stored anywhere else.

- Packaging: `make build|dmg|install|universal`, version from `git describe` into `main.version` via ldflags (`organizer version`, shown in the top bar). `scripts/make-dmg.sh` uses hdiutil only. `.github/workflows/release.yml` builds a universal app on tags `v*`, signs and notarizes only when the Developer ID secrets exist, and attaches the DMG to a GitHub Release. Bundle id `cl.antipan.organizer`, min macOS 12. Logs: `~/.local/share/organizer/organizer.log`.

## Commands

```bash
go test ./...                                  # unit tests, fixtures in testdata/home
UPDATE_GOLDEN=1 go test ./internal/cli/        # refresh the status golden file
go run . status | board | doctor | sync        # CLI against the real home
go run . prompt <initiative-id> [--run]        # agent review prompt, or open a terminal running it
wails dev                                      # app + http://localhost:34115 for browser dev
wails build                                    # build/bin/organizer.app
wails generate module                          # regenerate frontend/wailsjs after changing bound types
firebase deploy --only firestore:rules --project <p> # after editing firestore.rules
```

## Conventions

- Config: `~/.config/organizer/config.yaml`. Cache: `~/.local/share/organizer/state.json`.
- Bound Go types need json tags; the Wails generator turns a field-name collision into
  a duplicate TypeScript identifier (that is why the initiative's origin machine is `created_on`).
- `wails dev` builds into the same `build/bin/` as `wails build` and removes its binary on exit, leaving an empty `.app`. After any `wails dev` session, run `wails build` again before launching the app from Finder.
- Card statuses are a closed set: now, blocked, next, done. Do not add one here; change the skill.
